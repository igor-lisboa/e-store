# Verify quality

Read `AGENTS.md`, the affected specialty specs, `pom.xml`, CI configuration, and relevant tests before choosing checks. Use the repository root for commands. For a documentation-only change, validate its links, examples, or skill structure as applicable; do not invent application tests that add no behavioral evidence.

## Decide what the tests must prove

Map each changed requirement or regression to its observable result and the test layer that can prove it. Cover successful behavior and relevant boundaries, invalid input, failure handling, permissions, and persistent side effects. Prioritize account isolation, credentials, CSRF, stock, checkout consistency, and migrations when those areas change.

- Unit tests prove domain rules or use-case decisions with isolated dependencies.
- Integration tests exercise real boundaries: JDBC against disposable MySQL, migrations, transactions, and HTTP/container behavior. A servlet test with mocked requests/services is a unit test, not container integration evidence.
- Browser E2E tests prove user journeys through rendered forms, sessions, redirects, and real backend behavior. Static template checks cannot prove a browser flow works.

Do not require redundant tests at every layer for trivial changes. Explain which layers prove the behavior and any material coverage gaps.

## Reject shallow tests

For each test, identify the plausible defect it would catch. Reject or improve tests that only assert a mock's configured return, trivial getters/setters, object existence, private implementation details, source wording, or a method call without a meaningful contract. Boundary-call verification is useful when it proves an invariant, such as preventing a write after failed authorization.

Expected results must come from requirements or fixtures, not from copying the implementation's calculation. Assert the important output/state and absence of forbidden side effects. Error tests must fail if no error occurs; never swallow unexpected exceptions or print them and pass. Avoid broad assertions that unrelated failures could satisfy.

Keep tests deterministic and independent: fixed clocks/random sources when relevant, owned fixture data, explicit cleanup, no test-order dependence, and no production database. Mock external boundaries rather than the behavior under test. For a regression, demonstrate that the test fails for the original bug when feasible; targeted mutation testing can provide additional evidence for critical rules.

## Assess coverage honestly

Review the behavior-to-test mapping alongside uncovered branches and failure paths. JaCoCo reports are generated by `mvn verify` under `target/site/jacoco/`. Inspect measured line/branch results with their scope. There is no coverage threshold gate: do not invent percentages or infer strong coverage from test counts. Do not exclude production logic or add meaningless assertions to improve a number.

Static repository/OpenAPI checks supplement behavioral tests. A green schema check or high line coverage alone cannot establish correctness. Track missing integration/E2E coverage explicitly in `TODO.md`.

## Verify tests and build

Run focused tests during development, then verify the final state with the required suites and packaging:

```sh
python scripts/test_repository_contracts.py
python -m pip install -r scripts/requirements.txt
python scripts/validate_openapi.py
mvn -B clean verify
```

`clean verify` runs default isolated tests, H2 JDBC checks, and packages the WAR. It excludes the MySQL and legacy database/Cucumber suites. Create an explicitly disposable schema named `e_store_integration`, set `TEST_MYSQL_URL`, `TEST_MYSQL_USER`, and `TEST_MYSQL_PASSWORD`, then run:

```sh
mvn -B -Pmysql-integration clean verify
mvn -B -Plegacy-integration test
```

Both database profiles deliberately clean and reseed the guarded test schema per case. Never use production credentials. The MySQL profile tests migration apply/validate/reapply, checkout rollback, decimal totals, repeated checkout, address ownership, and competing stock allocation. The legacy profile also sets application connection variables to the guarded test database.

Run browser smoke tests with `python scripts/run_browser_smoke.py` after installing `scripts/requirements-browser.txt` and a Playwright Chromium browser. The runner launches and stops a local servlet container. Smoke tests cover forms/CSRF, all four locale selections, Swagger rendering, redirect restrictions, and guest access.

Enable database journeys with `STORE_DATABASE_E2E=1` and application database variables pointing to `e_store_integration`. Exercise both `ALLOW_DEMO_CHECKOUT=true` and `false`. These journeys verify customer registration/login/logout, favorites, escaped reviews, cart changes, addresses, checkout stock changes or denial, and administrator product/stock management with customer mutation denial. They mutate fixtures; reset with the MySQL profile between independent runs. Review remaining routes and failure paths rather than assuming these journeys cover the entire application.

For migration changes, verify clean application, validation, and a second migration run against the same disposable database. Full Compose startup is a separate environment check; native MySQL/Tomcat tests do not prove the Compose workflow succeeds.

Inspect exit codes and test reports for failures, errors, skipped tests, and unexpected zero-test runs. Confirm the expected WAR and runner artifacts exist after packaging. `mvn test` alone is not build/package verification. If relevant code changes after a check, rerun the affected checks against the final state.

Fix failures caused by the change and rerun their checks. Do not skip, disable, weaken, or relabel failing tests merely to get a green result. Investigate pre-existing failures, describe their impact, and track unresolved failures explicitly. Missing Java/Maven/Docker or service access means verification is blocked, not passed. Continue useful review and static validation when runtime checks are unavailable.

## Completion report

Report changed behavior covered, meaningful tests added/updated, commands and results, suite scope, skipped or unavailable suites, build artifact verification, and remaining gaps. Say "all tests pass" only when every required suite actually ran successfully for the final state. Otherwise name exactly which suites passed and which remain unverified. Update specs and the backlog with the evidence.
